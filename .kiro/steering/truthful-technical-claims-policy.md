# GhostOps — Truthful Technical Claims Policy

## Purpose

GhostOps is an evidence-first platform. It would be deeply ironic for the platform itself to make claims about its own behaviour that are not supported by evidence. This policy defines the standard for all technical claims made in documentation, UI copy, error messages, and README text.

---

## The Three-Tier Rule Applies Internally

The same OBSERVED / INFERRED / HYPOTHESIS taxonomy used for incident analysis applies to claims about the Platform itself:

| Tier | Applies when |
|---|---|
| OBSERVED | The claim is verifiable by running a specific test or reading a specific line of code |
| INFERRED | The claim follows from documented design decisions, even if not directly testable in isolation |
| HYPOTHESIS | The claim is a reasonable expectation not yet verified by a test |

Any HYPOTHESIS claim in documentation or UI copy must be labelled as such ("expected to", "designed to") rather than stated as fact.

---

## Prohibited Claim Patterns

### 1. Performance claims without measurement

❌ "GhostOps analyses incidents instantly."
✅ "GhostOps analyses the three bundled demo scenarios in under 500ms on a modern laptop (measured with Chrome DevTools Performance tab)."

No performance claim may appear in documentation or UI copy unless it is backed by a reproducible benchmark. Benchmark setup and results must be stored in `docs/benchmarks/`.

### 2. Accuracy claims without ground truth

❌ "GhostOps accurately identifies root causes."
✅ "For the three bundled demo scenarios, GhostOps produces the expected Claims output as verified by the scenario integration tests."

Claims about analysis quality must be scoped to verified demo scenarios, not generalised across arbitrary incidents.

### 3. Completeness claims without enumeration

❌ "GhostOps supports all log formats."
✅ "GhostOps ingests plain-text log files, JSON CI output files, JSON deployment event files, and Git log output produced by `git log --format=json`."

Support claims must enumerate the exact formats tested. "All", "any", "every" are forbidden unless the enumeration is exhaustive and tested.

### 4. Security claims without verification

❌ "GhostOps is secure."
✅ "GhostOps applies a Content Security Policy that blocks outbound connections (verified by the CSP test in `tests/unit/csp.test.ts`). All JSON input is validated before use (verified by the ingester unit tests)."

Security properties must reference the specific controls implemented and the tests that verify them.

### 5. AI-generated claims not verified against code

If any documentation text is generated by an AI assistant (including Codex), the author must verify every technical claim in that text against the actual implementation before committing. A claim that the AI generated but that does not match the code must be corrected before the PR is merged.

## Error Message Standards

Error messages shown in the UI or written to the console must:

1. State what happened, not what the system "tried" to do.
2. Reference the specific file or record that caused the error.
3. Not assert that the user made a mistake unless the input violates a documented constraint.
4. Not promise that the error "will be fixed" or that a retry "will succeed" unless the system can verify this.

**Bad:** "Something went wrong processing your file. Please try again."
**Good:** "Could not parse `deploy-events.json`: expected an array at root, got object. Check that the file follows the deployment event format described in the documentation."

---

## README Accuracy Rules

The README must include a "What this tool does and does not do" section with:

- An explicit list of supported input formats (with file format descriptions).
- An explicit list of claim types the engine can produce.
- A statement that root-cause claims require at least two corroborating sources.
- A statement that the tool does not connect to the internet during analysis.
- A statement that analysis results depend entirely on the evidence provided and may be incomplete if evidence is missing.

The README must not claim the tool "solves" incidents, "finds" root causes autonomously, or "eliminates" the need for human judgement.

---

## Review Checklist

Before merging any PR that changes documentation, UI copy, or error messages, verify:

- [ ] Every performance claim references a specific benchmark.
- [ ] Every accuracy claim is scoped to verified scenarios.
- [ ] Every format support claim enumerates tested formats.
- [ ] Every security claim references a specific control and its test.
- [ ] No "always", "never", "all", "every", "guaranteed" unless provably true.
- [ ] No AI-generated claims that were not verified against the implementation.
- [ ] Error messages follow the error message standards above.
