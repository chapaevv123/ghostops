# Requirements Document

## Introduction

GhostOps is an evidence-first software incident reconstruction platform built for Kiroween 2026 (Frankenstein category). It ingests exported logs, CI output records, deployment events, and Git change records and reconstructs a verified incident timeline. Every claim the platform surfaces must be grounded in source evidence. The platform enforces a strict three-tier claim taxonomy (OBSERVED, INFERRED, HYPOTHESIS) and refuses to assert a root cause unless the loaded evidence supports that conclusion. A working browser UI presents the timeline and evidence ledger. Three reproducible demo scenarios ship with the platform to validate the engine and showcase its capabilities.

---

## Glossary

- **Platform**: The GhostOps application, comprising the analysis engine, evidence ledger, claim verifier, timeline reconstructor, and browser UI.
- **Evidence_Ingester**: The subsystem responsible for parsing and normalising raw input files (logs, CI output, deployment events, Git records).
- **Evidence_Ledger**: The persistent in-memory store that holds every normalised evidence item and its provenance metadata.
- **Claim_Verifier**: The subsystem that classifies each generated claim and refuses to emit unsupported root-cause assertions.
- **Timeline_Reconstructor**: The subsystem that orders verified claims chronologically and assembles the incident timeline.
- **UI**: The browser-based interface that renders the timeline, evidence ledger, and gap report.
- **Analyst**: A human user who loads evidence files and reviews the reconstructed incident.
- **Evidence_Item**: A single normalised entry in the Evidence_Ledger, derived from one source record, with a timestamp, source reference, and raw excerpt.
- **Claim**: A statement generated by the analysis engine that asserts something about the incident.
- **OBSERVED**: A claim classification for facts that are directly and unambiguously present in at least one Evidence_Item.
- **INFERRED**: A claim classification for conclusions drawn by correlating two or more Evidence_Items but not directly stated in any single item.
- **HYPOTHESIS**: A claim classification for possible explanations that lack sufficient Evidence_Items to be classified as INFERRED.
- **Gap**: A missing evidence condition identified by the Claim_Verifier where a chain of reasoning cannot be completed due to absent evidence.
- **Demo_Scenario**: One of three bundled incident datasets used to demonstrate and validate the Platform's capabilities reproducibly.
- **Analysis_Engine**: The deterministic subsystem that produces Claims from the Evidence_Ledger.
- **Evidence_Bundle**: A complete set of input files for a single incident analysis session.
- **Source_Reference**: A pointer back to the originating file, line number, and byte offset for an Evidence_Item.
- **Confidence_Score**: A numerical value in the range [0.0, 1.0] expressing the strength of evidence supporting an INFERRED or HYPOTHESIS claim.

## Requirements

### Requirement 1: Evidence Ingestion

**User Story:** As an Analyst, I want to load exported logs, CI output files, deployment event records, and Git change records into the Platform, so that all relevant evidence for an incident is available for analysis.

#### Acceptance Criteria

1. THE Evidence_Ingester SHALL accept plain-text log files, structured JSON CI output files, structured JSON deployment event files, and Git log output files as valid input formats.
2. WHEN a file is loaded, THE Evidence_Ingester SHALL parse each record into a normalised Evidence_Item containing a timestamp, a source type label, a Source_Reference, and the verbatim raw excerpt from the source file.
3. IF a file cannot be parsed because its format does not match any supported type, THEN THE Evidence_Ingester SHALL reject the file and return a structured error message identifying the file name and the format violation detected.
4. IF a record within a valid file contains a malformed or absent timestamp, THEN THE Evidence_Ingester SHALL record the item with a null timestamp and attach a Gap annotation indicating the timestamp could not be resolved.
5. WHEN ingestion of a file completes successfully, THE Evidence_Ingester SHALL emit a structured ingestion summary reporting the file name, the count of Evidence_Items produced, and the count of records skipped with reasons.
6. THE Evidence_Ingester SHALL process all input files deterministically, producing the same Evidence_Ledger state for the same set of input files on every invocation.
7. WHEN an Evidence_Bundle contains more than one file, THE Evidence_Ingester SHALL merge all Evidence_Items into a single Evidence_Ledger, preserving each item's Source_Reference to its originating file.

---

### Requirement 2: Evidence Ledger

**User Story:** As an Analyst, I want all ingested evidence to be stored in a queryable ledger that preserves provenance, so that every claim can be traced back to its source.

#### Acceptance Criteria

1. THE Evidence_Ledger SHALL store each Evidence_Item with a unique identifier, its timestamp (or null), its source type, its Source_Reference, and its verbatim raw excerpt.
2. THE Evidence_Ledger SHALL remain immutable after ingestion; no Evidence_Item SHALL be modified or deleted during analysis or rendering.
3. WHEN queried by source type, THE Evidence_Ledger SHALL return all Evidence_Items matching that type in ascending timestamp order.
4. WHEN queried by time range, THE Evidence_Ledger SHALL return all Evidence_Items whose timestamps fall within that range, inclusive of both boundaries.
5. THE Evidence_Ledger SHALL expose a count of all stored Evidence_Items and a count of items with null timestamps at any point after ingestion.
6. FOR ALL Evidence_Items stored in the Evidence_Ledger, the Source_Reference SHALL point to a location that exists within the originally loaded input file.

---

### Requirement 3: Claim Classification

**User Story:** As an Analyst, I want every claim the Platform generates to be classified as OBSERVED, INFERRED, or HYPOTHESIS, so that I can immediately understand the epistemic strength of each statement.

#### Acceptance Criteria

1. THE Claim_Verifier SHALL classify every Claim as exactly one of OBSERVED, INFERRED, or HYPOTHESIS before the Claim is added to the timeline.
2. THE Claim_Verifier SHALL classify a Claim as OBSERVED only when the claim text is supported by a direct, unambiguous match in at least one Evidence_Item's raw excerpt.
3. THE Claim_Verifier SHALL classify a Claim as INFERRED only when the claim is supported by the correlation of two or more Evidence_Items and no single Evidence_Item alone supports the full claim.
4. THE Claim_Verifier SHALL classify a Claim as HYPOTHESIS when the supporting Evidence_Items are insufficient to meet the INFERRED threshold.
5. WHEN a Claim is classified as INFERRED or HYPOTHESIS, THE Claim_Verifier SHALL attach a Confidence_Score in the range [0.0, 1.0] computed from the ratio of supporting Evidence_Items to the total items consulted.
6. WHEN a Claim is classified as OBSERVED, THE Claim_Verifier SHALL attach one or more Source_References identifying every Evidence_Item that directly supports the claim.
7. THE Claim_Verifier SHALL output each classified Claim as a structured record containing: claim text, classification, Confidence_Score (when applicable), and all supporting Source_References.

---

### Requirement 4: Root-Cause Refusal

**User Story:** As an Analyst, I want the Platform to refuse to assert a root cause unless the evidence directly supports that conclusion, so that I never receive a speculative root-cause finding presented as fact.

#### Acceptance Criteria

1. WHEN the Analysis_Engine produces a root-cause Claim, THE Claim_Verifier SHALL verify that the claim is supported by at least two corroborating Evidence_Items before emitting it.
2. IF a root-cause Claim cannot be supported by at least two corroborating Evidence_Items, THEN THE Claim_Verifier SHALL replace the claim with an explicit unsupported-root-cause notice that identifies what evidence is present and what evidence is missing.
3. THE Claim_Verifier SHALL never emit a root-cause Claim with a classification of HYPOTHESIS as a definitive conclusion; HYPOTHESIS root-cause claims SHALL be labelled as speculative and presented separately from confirmed findings.
4. WHEN the Claim_Verifier emits an unsupported-root-cause notice, THE UI SHALL render the notice visually distinct from confirmed and inferred claims.
5. THE Analysis_Engine SHALL generate at most one root-cause Claim per analysis session; additional potential causes SHALL be emitted as HYPOTHESIS claims with individual Confidence_Scores.

---

### Requirement 5: Gap Detection

**User Story:** As an Analyst, I want the Platform to surface missing evidence gaps so that I know exactly what additional data I would need to strengthen or complete the analysis.

#### Acceptance Criteria

1. WHEN the Analysis_Engine cannot complete a causal chain due to absent Evidence_Items, THE Claim_Verifier SHALL generate a Gap record describing the missing evidence type, the time window in which it is missing, and the claim it would support.
2. THE Claim_Verifier SHALL generate a Gap record for each ingested log file type that produced zero Evidence_Items after parsing.
3. THE Evidence_Ledger SHALL maintain a Gap list that is populated during ingestion and analysis and is accessible to the UI at render time.
4. WHEN the Gap list contains one or more records, THE UI SHALL display a dedicated gap report section listing each Gap with its description and the claim affected.
5. IF the Analyst loads additional evidence files that resolve one or more existing Gaps, THEN THE Claim_Verifier SHALL remove the resolved Gap records and re-classify any Claims that depended on the now-available evidence.

---

### Requirement 6: Timeline Reconstruction

**User Story:** As an Analyst, I want a chronological incident timeline assembled from verified claims, so that I can understand the sequence of events that led to the incident.

#### Acceptance Criteria

1. THE Timeline_Reconstructor SHALL order all OBSERVED and INFERRED Claims by their associated Evidence_Item timestamps in ascending order.
2. WHEN two Claims carry the same timestamp, THE Timeline_Reconstructor SHALL order them by source type priority: Git records first, then deployment events, then CI output, then log entries.
3. THE Timeline_Reconstructor SHALL exclude HYPOTHESIS Claims from the primary timeline and place them in a separate speculative events section.
4. WHEN the timeline is assembled, THE Timeline_Reconstructor SHALL insert Gap markers at time positions where evidence is absent, indicating the duration of the gap.
5. THE Timeline_Reconstructor SHALL produce a deterministic output: given the same Evidence_Ledger and Claims, the assembled timeline SHALL be identical on every invocation.
6. WHEN a Claim references multiple Evidence_Items with different timestamps, THE Timeline_Reconstructor SHALL place the Claim at the timestamp of its earliest supporting Evidence_Item.

---

### Requirement 7: Browser UI

**User Story:** As an Analyst, I want a working browser interface that lets me load evidence files, view the timeline, inspect individual claims and their evidence, and review the gap report, so that I can conduct an incident analysis without using command-line tools.

#### Acceptance Criteria

1. THE UI SHALL provide a file-picker control that accepts one or more files for ingestion and displays the ingestion summary after loading completes.
2. THE UI SHALL render the incident timeline as a vertically scrolling list of events, each labelled with its timestamp, claim text, and classification badge (OBSERVED, INFERRED, or HYPOTHESIS).
3. WHEN an Analyst clicks a Claim entry in the timeline, THE UI SHALL display a detail panel showing the claim text, classification, Confidence_Score (when applicable), and all supporting Source_References with verbatim excerpts.
4. THE UI SHALL render OBSERVED, INFERRED, and HYPOTHESIS badges using visually distinct colours so that the classification is identifiable without reading the label text.
5. THE UI SHALL render the gap report section below the timeline, listing each Gap record with its description and the affected claim.
6. THE UI SHALL render unsupported-root-cause notices in a visually distinct style that differentiates them from confirmed and inferred claims.
7. WHEN the Evidence_Ledger contains zero Evidence_Items, THE UI SHALL display an empty-state message prompting the Analyst to load evidence files.
8. THE UI SHALL function correctly in a modern web browser without requiring a backend server or network access beyond the initial page load.
9. WHERE the Analyst's browser supports the File System Access API, THE UI SHALL use it to read files locally; WHERE the browser does not support it, THE UI SHALL fall back to the standard HTML file input element.

---

### Requirement 8: Deterministic Analysis Engine

**User Story:** As an Analyst, I want the analysis to produce the same output every time for the same input, so that incident findings are reproducible and auditable.

#### Acceptance Criteria

1. THE Analysis_Engine SHALL produce the same set of Claims, Gap records, and timeline order for the same Evidence_Bundle on every invocation, regardless of execution environment.
2. THE Analysis_Engine SHALL not rely on the current wall-clock time, random number generation, or external service calls during analysis.
3. WHEN the Analysis_Engine completes an analysis, THE Platform SHALL expose a determinism-check interface that accepts a second run of the same Evidence_Bundle and asserts that the two outputs are byte-for-byte identical.
4. THE Analysis_Engine SHALL execute all analysis steps in a fixed, documented order that does not vary between invocations.

---

### Requirement 9: Demo Scenarios

**User Story:** As an Analyst, I want three bundled demo scenarios that I can load at any time to see the Platform's full capabilities with realistic incident data, so that I can evaluate and demonstrate the tool without needing my own evidence files.

#### Acceptance Criteria

1. THE Platform SHALL include exactly three Demo_Scenarios, each consisting of a complete Evidence_Bundle, an expected Claims output, an expected timeline order, and an expected Gap list.
2. WHEN a Demo_Scenario is loaded, THE Platform SHALL produce Claims, a timeline, and a Gap list that match the pre-defined expected outputs for that scenario.
3. THE Demo_Scenarios SHALL cover the following incident archetypes: a deployment-caused outage, a dependency version conflict uncovered via CI output, and a cascading failure initiated by a log-evidenced resource exhaustion event.
4. THE Demo_Scenarios SHALL include at least one OBSERVED Claim, at least one INFERRED Claim, at least one HYPOTHESIS Claim, and at least one Gap record each.
5. THE Demo_Scenarios SHALL be fully self-contained within the Platform repository and SHALL not require network access to load.
6. WHEN the expected output for a Demo_Scenario does not match the Analysis_Engine's actual output, THE Platform SHALL surface a scenario validation failure message identifying which Claims or Gap records differ.

---

### Requirement 10: Evidence Integrity

**User Story:** As an Analyst, I want assurance that the Platform never silently modifies, omits, or fabricates evidence, so that I can trust the analysis output.

#### Acceptance Criteria

1. THE Evidence_Ingester SHALL preserve the verbatim raw excerpt of each source record without modification, truncation, or normalisation of the text content.
2. THE Claim_Verifier SHALL not generate a Claim that references a Source_Reference that does not exist in the Evidence_Ledger.
3. IF the Evidence_Ingester encounters a record that it cannot parse, THEN THE Evidence_Ingester SHALL log the unparseable record verbatim as a skipped-record entry rather than silently discarding it.
4. THE Platform SHALL not generate Claim text that asserts facts not derivable from the contents of the Evidence_Ledger.
5. WHEN an Analyst exports an analysis session, THE Platform SHALL include the full Evidence_Ledger, all Claims with their Source_References, all Gap records, and the assembled timeline in the export package.

---

### Requirement 11: Parsing and Serialisation Round-Trip

**User Story:** As a developer, I want all internal data structures to serialise and deserialise without data loss, so that saved sessions and exported evidence bundles are faithful representations of the in-memory state.

#### Acceptance Criteria

1. THE Evidence_Ingester SHALL parse supported file formats into Evidence_Items that fully represent every field present in the source record.
2. THE Platform SHALL provide a serialiser that converts the Evidence_Ledger, Claims, Gap list, and timeline to JSON.
3. THE Platform SHALL provide a deserialiser that restores the Evidence_Ledger, Claims, Gap list, and timeline from the JSON produced by the serialiser.
4. FOR ALL valid Evidence_Bundles, serialising then deserialising then serialising SHALL produce JSON that is structurally identical to the first serialisation output (round-trip property).
5. WHEN a deserialised session is re-analysed, THE Analysis_Engine SHALL produce Claims, a timeline, and a Gap list identical to the output of the original analysis session.
